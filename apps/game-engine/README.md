# Game engine — каркас графического движка на WebGPU

Мини-приложение проекта Mini Apps: страница только грузит файлы, шейдер (WGSL) и скрипты
лежат отдельно, вывод шейдера показывается в рамке.

Адрес: <https://dperegudov61.github.io/mini-apps/apps/game-engine/>

Луч на каждый пиксель считается на GPU аналитически (точные пересечения с аналитическими
телами, без марша по объёму). Сцены — наборы объектов, окружения и камеры — собираются
на процессоре: шейдер о них ничего не знает, он получает готовые примитивы и числа.

Сцен сейчас две: **стенд** (пьедестал, ступени, обелиски, парящий куб, сферы на орбитах)
и **бенчмарк** (куб 26×26×26 из сфер, которые появляются по одной — проверка нагрузки
и стабильности).

## Как запускать

* **По адресу выше** — основной путь: ничего не собирается, Pages отдаёт файлы как есть,
  правка в репозитории видна после `git push` и обновления страницы (≈1 минута на сборку Pages).
* Локально — только через `http` (любой статический сервер в папке `mini-apps/`).
  Двойным щелчком по `index.html` с диска **не запустится**: браузер не даёт читать соседние
  файлы (`fetch` шейдеров заблокирован), страница честно об этом скажет.
  Серверных файлов внутри приложения нет — это чистая статика.

Нужен браузер с WebGPU: Chrome или Edge 113+. Нет адаптера — подсказки на самой странице
покажут причину.

## Управление

| действие | что делает |
|---|---|
| перетаскивание мышью / пальцем | камера облетает цель |
| колесо | приближение и отдаление |
| `W` `A` `S` `D` | двигают цель по земле |
| `Q` `E` | цель вниз / вверх |
| стрелки | поворот камеры |
| «Сброс» | ползунки **этой** сцены и камера — к значениям по умолчанию, замеры заново |
| «Пауза» | сцена замирает (камера, ползунки и замеры продолжают работать) |

Камера у каждой сцены своя: её начальное положение описано в `camera` описания сцены.

## Сцены

Сцена — это независимый набор:

* **объектов** — массив `{kind: 'sphere' | 'cone' | 'box', …}`;
* **параметров окружения** — высота солнца, яркость, звёзды, разметка земли;
* **камеры** — цель, поворот, расстояние, угол обзора;
* **своих ползунков и переключателей** — у каждой сцены свой набор, свои значения
  и своя память (`scene.<id>` в `localStorage`).

Общее для всех сцен — только **настройки рендера** (масштаб кадра, авто-масштаб, тени)
и инструменты производительности. Они лежат в отдельном блоке панели и в отдельном ключе
памяти (`gfx`).

Устройство:

```
js/scene/registry.js   реестр: GE.Scenes.define({...}) — описание сцены и фабрика create()
js/scene/pack.js       солнце (GE.sunFor) и упаковка сцены в буферы (GE.packObjects, GE.writeFrame)
js/scene/demo.js       сцена «стенд»     → GE.Scenes.define({ id: 'demo',  … })
js/scene/bench.js      сцена «бенчмарк»  → GE.Scenes.define({ id: 'bench', … })
```

Описание сцены:

```js
GE.Scenes.define({
  id: 'demo',                       // ключ в памяти и в списке
  label: 'game-engine.sceneDemo',   // ключ надписи (strings.tsv), fb — английский запас
  note: 'game-engine.sceneDemoNote',
  camera: { target: [0, 1.5, 0], yaw: 0.75, pitch: 0.32, distance: 12.5 },
  params:  [GE.SceneParts.sun(30), GE.SceneParts.speed(1), GE.SceneParts.exposure(1)],
  toggles: [GE.SceneParts.stars(1), GE.SceneParts.grid(1)],
  actions: [],                      // свои кнопки: у бенчмарка — «заполнить сразу»
  create: function () { return new DemoScene(); }
});
```

Живой набор объектов, который отдаёт `create()`, обязан уметь немного:

| поле / метод | смысл |
|---|---|
| `objects` | массив примитивов, который каждый кадр уезжает на GPU |
| `env` | `{sunHeight, exposure, stars, grid}` — значения окружения кадра |
| `sun` | `GE.sunFor(env.sunHeight)`: направление, цвет, сила, свет неба |
| `time` | игровое время, уходит в шейдер (звёзды, дизеринг) |
| `update(dt, settings)` | движение, появление объектов; `dt = 0` — пауза |
| `reset()` | вернуть сцену в начало |
| `status(settings)` | необязательная строка состояния под панелью |

Порядок в списке на странице — порядок вызовов `define()`; подключение файлов — в конце
`index.html`. Состояние (какая сцена открыта, какие ползунки) запоминается в `localStorage`.

## Сцена «стенд»

`js/scene/demo.js`:

* пьедестал (куб) и сфера на нём — центр композиции;
* три ступени из кубов, уходящие вправо;
* парящий куб, качающийся по высоте;
* три конуса-обелиска по краям;
* три сферы, летающие по орбитам разного радиуса и с разной скоростью.

Движение — только на процессоре: `update()` пересчитывает координаты, `packObjects()`
раскладывает их по буферу, шейдер о времени и орбитах ничего не знает.
Ползунки: высота солнца (−90…+90°), скорость анимации, яркость; переключатели: звёзды,
разметка земли.

## Бенчмарк «куб сфер 26×26×26»

`js/scene/bench.js`: 17576 сфер (`26³`) с шагом сетки 1 м и радиусом 0.30 м, центр куба —
на высоте 13 м. **Ползунок «объектов» задаёт точное число тел (0…17576)** — это и есть прямая
зависимость «сколько тел → сколько мс»: подвинули ползунок, линия времени кадра встала на
новую высоту. Ползунок «сфер в секунду» (> 0) заставляет сцену расти самой — старый способ
смотреть, как движок держит наплыв; по умолчанию он 0, чтобы число не «уплывало».
Кнопка «заполнить сразу» ставит все 17576.

Замеры на этой машине (nvidia pascal, кадр 735×413 = 0.30 Мпикс, время — до конца работы
GPU, без ограничения частотой экрана, поэтому цифры — это именно цена отрисовки):

| тел | тени выключены | тени включены |
|---|---|---|
| 0 | 1.0 мс | 0.9 мс |
| 100 | 2.5 мс | 4.3 мс |
| 340 | 7.8 мс | 12.3 мс |
| 1000 | 21.3 мс | 37.0 мс |
| 4096 | 77.2 мс | 140.7 мс |

Рост ровно линейный по числу тел: цена кадра = пиксели × тела (+ пиксели × небо/земля).
Тени на 4096 телах — почти половина кадра: на каждый освещённый пиксель идёт свой луч к
солнцу по всем телам. Потолок буфера примитивов — 17576 (`MAX_PRIMS` в `js/gfx/renderer.js`,
это 824 КБ на видеокарте).

## Процессор: сколько стоит кадр и можно ли второе ядро

Замер `GE.packObjects` в Node (тот же `js/scene/pack.js`), сферы куба 26³:

| тел | упаковка | сравнение с прошлым кадром |
|---|---|---|
| 4096 | 0.15 мс | сотые доли мс |
| 17576 | 0.53 мс | ~0.2 мс (211 тыс. float) |

Плюс `writeBuffer` на 824 КБ за каждый нарисованный кадр. На телефоне умножайте
примерно вчетверо — получается 2–5 мс на кадр, пока ещё далеко от 16.7 мс бюджета
60 Гц. Работа сцены (движение орбит, рост тел) — отдельно и по числу тел.

Почему «просто добавить ядра» не получается:

* **WebGPU не распараллеливается по ядрам.** Устройство и очередь одни, отправлять
  работу может только главный поток: в Worker-фабрике адаптер выдаёт устройство,
  но подчиняется другому потоку — на общую картинку это не делится;
* **SharedArrayBuffer в опубликованном приложении недоступен.** Он требует
  `crossOriginIsolated`, то есть заголовков COOP/COEP; GitHub Pages их не отдаёт;
* значит остаётся путь без общей памяти: **не делить кадр, а перекрывать**. Worker держит
  свой кусок сцены в плоских типизированных массивах, собирает буфер следующего кадра
  и отдаёт его главному потоку передачей владения (`postMessage(..., [buf])` — без
  копирования), пока видеокарта рисует предыдущий кадр. Стоимость: двойная буферизация
  (2 × 824 КБ) и один кадр задержки.

Порядок действий, когда цифра `cpu` в панели вырастет: сначала один Worker на упаковку
с двойной буферизацией (чаще всего этого достаточно), и только потом N = `hardwareConcurrency − 2`
воркеров с разбиением тел на полосы. Сама упаковка сейчас — три прохода по массиву
объектов (сферы, конусы, кубы): если понадобится, сводится к одному проходу с подсчётом
заранее.

## Настройки рендера (общие для всех сцен)

* **масштаб рендера** — кадр считается в 0.01…4× от размера полотна: главный рычаг нагрузки
  (лучи считаются на каждый пиксель). 2.5×, 3× и 4× — не для красоты: так проверяют движок
  за старое слабое устройство, не имея его под рукой;
* **авто-масштаб** — работает только пока картинка меняется: держит кадр в пределах одного
  обновления экрана, меняя разрешение множителем в пределах до **0.01×** — на таком пределе
  от картинки остаются единицы пикселей, зато видно нижнюю границу цены кадра. Когда
  движение кончилось, разрешение поднимается к полному — настолько, насколько влезает в
  бюджет одного статичного кадра (см. «Авто-масштаб: почему по интервалу» ниже);
* **тени** — лучи к солнцу; самая дорогая часть кадра, особенно на 17576 примитивах;
* **нагрузка на ядро** (core limit, 100/75/50/25%) — какую долю времени шейдеру
  разрешено занимать видеоядро. Внутри кадра работа не дробится (прервать шейдер
  нельзя), но между кадрами остаётся простой — и слабая машина не встаёт целиком:
  на 50% кадр и простой равны, fps падает вдвое, зато меню и система дышат;
* **отладка поверх кадра** — зелёная строка в левом верхнем углу рамки (fps, время кадра,
  p95, худший, разрешение, масштаб, число примитивов, cpu/gpu и занятость ядра); галочка убирает её,
  панель с теми же цифрами остаётся на месте.

## Инструменты производительности

* **отладка поверх кадра** — та же сводка контрастно-зелёной строкой в левом верхнем углу
  рамки: видно, не отрываясь от картинки (галочка «отладка поверх кадра» в настройках рендера),
  и одновременно в панели ниже — полные цифры и график;
* **график времени кадра** — по горизонтали последние 180 кадров (≈3 с), по вертикали
  миллисекунды; линия 60 Гц сплошная, 30 Гц — пунктир. **Вторая, тусклая кривая — число тел**
  по своей шкале: видно, как время кадра идёт вслед за количеством;
* **цифры**: fps, среднее время кадра, лучший и худший кадр за окно, 95-й процентиль
  (по нему видно рывки, которые среднее прячет), время процессора в кадре (cpu, мс),
  время прохода на GPU (gpu, мс), **примитивов** (сколько тел сейчас), **занятость ядра**
  (сколько процентов времени видеоядро занято работой шейдера) и **мс на Мпикс**
  (время кадра на мегапиксель — одна мерка для любой карты и любого масштаба; показывается
  «—», пока кадр держит 60 Гц, потому что там время кадра — это частота экрана, а не работа).

Время GPU берётся из `timestamp-query`: две метки вокруг прохода рендера, результат читается
обратным копированием. Не всякий браузер это разрешает: у нового Chromium метка ставится на
кодировщике команд, у части версий — только внутри прохода (и только с экспериментальной
фичей). Если нельзя ни так, ни так — в колонке `gpu` честно стоит «—», остальные измерения
работают.

График и статистика считают кадры любой длины, включая медленные (раньше кадры дольше
250 мс выбрасывались как «переключение вкладки» — и на 4× график молчал). Отбрасываются
только кадры при скрытой вкладке и первые три кадра после сброса (компиляция шейдера и
первый показ кадра — они в сотни раз длиннее обычных); шкала графика поднимается под
худший кадр вплоть до 4000 мс.

## Цикл кадров: один кадр в полёте

Кадр подаётся на GPU, и **процессор ждёт его выполнения** (`queue.onSubmittedWorkDone`),
и только потом просит следующий `requestAnimationFrame`.

Почему так: подавать кадр каждый тик экрана при тяжёлом кадре нельзя. Кадр на 4096 телах при
1× стоит 140 мс, то есть цикл на 60 Гц набирал бы около 8 секунд работы за каждую секунду
работы видеочипа — очередь `GPUQueue` росла бы без предела (за 10 секунд — минута отложенной
работы), видеоядро было бы занято на 100%, и вместе с ним вставали бы композитор браузера,
рабочий стол и весь интерфейс: меню не листается, ползунки не двигаются. С ожиданием в
очереди всегда не больше одного кадра, на видеокарте — одна работа, а главный поток свободен:
камера, меню и настройки отвечают, даже когда кадр считается сотни миллисекунд.

Время кадра в игровой логике — **реальное** (`dt` из `performance.now()`), без обрезки в
50 мс: если кадр длился 140 мс, сцена за эти 140 мс и сдвинется, иначе движение замедлялось
бы вместе с fps. Ограничение осталось одно — 2 с: страховка от возврата на вкладку и от сна
машины. По той же причине `fps` и среднее время кадра в инструментах — честные: это время от
кадра до кадра вместе с ожиданием.

### Ограничение нагрузки на ядро

Внутри одного кадра шейдер занимает вычислительное ядро целиком — прервать его
нельзя, и API «отдай шейдеру 50% ядра» в WebGPU нет. Зато есть доля времени в целом:
время от подачи кадра до его готовности (`onSubmittedWorkDone`) — это и есть занятость
ядра, и после кадра можно вставить паузу.

Настройка **нагрузка на ядро** (100 / 75 / 50 / 25%) задаёт именно эту долю: после
кадра длиной `T` цикл ждёт `T × (1/d − 1)`, где `d` — выбранная доля. При 50% и кадре
75 мс ждём ещё 75 мс: fps падает с 13 до ~7, но видеоядро половину времени свободно
для композитора, меню и всей системы. На быстрой машине настройка ничего не меняет:
кадр и так упирается в частоту экрана, и ядро занято единицы процентов.

Видно это в цифре **занятость ядра, %** — работа кадра / время от кадра до кадра (и в
отладочной строке как `core`). 100% — очередь не пустеет никогда, 50% — половину
времени ядро свободно.

### Простой: если картинке нечего менять

Перед подачей кадра процессор сверяет **содержимое** с прошлым кадром (`js/gfx/renderer.js`
→ `contentChanged()`): объекты, положение камеры, солнце, окружение. Разрешение кадра и
игровое время в сверку не входят — первое меняет сам движок (масштаб), второе идёт всегда.

Ход кадра (`app.js`):

| состояние | что происходит |
|---|---|
| `dynamic` | содержимое меняется: работает авто-масштаб, разрешение подстраивается под темп экрана |
| `up` | содержимое застыло: разрешение поднимается ступенями, каждая — настолько, насколько влезает в бюджет статичного кадра |
| `static` | картинка в полном разрешении, кадры не подаются вообще — ядро свободно |

В `static` на экране остаётся последний кадр в полном разрешении (1× или выбранный
масштаб, если он больше). Как только что-то меняется — камера, ползунок, появление
тел, — движок возвращается к рабочему масштабу движения и снова меряет заново.

### Авто-масштаб: почему по интервалу, а не по времени ядра

Первая версия авто-масштаба решала по времени кадра «от подачи до готовности»
(`queue.onSubmittedWorkDone()`) и по интервалу между кадрами. Оба варианта сломались
одинаково — и именно так, как это было видно на экране (масштаб только падал):

* **интервал** при цикле «один кадр в полёте» не бывает меньше одного обновления экрана:
  условие «поднимаем при среднем < 13.5 мс» на 60 Гц было недостижимо, а любой
  пропущенный кадр стоил сразу 33 мс и валил среднее — шаг вниз на каждом окне;
* **время готовности** на этом железе имеет пол около 13 мс (очередь сообщает о
  готовности синхронно с показом): лёгкий и средний кадр дают одно число, и по нему
  разрешение тоже ползло вниз — 1× → 0.49 → 0.34 → 0.24 → 0.17 при кадре, который
  давно влезал в бюджет.

Поэтому решает интервал, но с правильными правилами (всё в `adapt()` в `app.js`):

* период экрана `vsyncMs` — меньшее из виденных значений (60 Гц → 16.7, 120 Гц → 8.3);
* окно 0.4 с кадров **динамики** (статика и подъём в счёт не идут);
* `avg > vsync × 1.2` — не помещаемся: шаг вниз **по перегрузу** (√(vsync/avg)) —
  за один шаг долетаем туда, где цена кадра влезает, а не ползём по ×0.7;
* `avg ≤ vsync × 1.03` — помещаемся с запасом: шаг вверх — **проба**. Не влезла —
  возвращаемся на прежний масштаб и больше туда не лезем, пока не сменится число тел;
* **снижение перестало помогать** (шаг на 30% площади дал меньше 15% выигрыша) — дело
  не в разрешении: возвращаем картинку покрупнее и вниз больше не идём. Без этого
  правила масштаб уезжал в 0.04× на сцене, где упирается не пиксель, а сам кадр;
* **прогрев**: первые два кадра после смены состояния/масштаба (новый размер полотна,
  новая текстура) в счёт не идут — из-за них раньше разрешение падало при каждом
  переходе статика → динамика;
* потолок подъёма — выбранный ползунком масштаб (но не ниже 1×), а не `SCALE_MAX`:
  иначе заработавший подъём уезжает на 4× вместо 1×.

Подъём в статике считается по цене прошлого кадра: шаг = √(бюджет / цена), но не больше
×1.7 за кадр; бюджет одного статичного кадра — 120 мс. Ступень, которая в него не влезает,
не рисуется вовсе — иначе на слабом телефоне один такой кадр подвесил бы всю систему;

Защита от сюрпризов:

* смена размера полотна и возврат на вкладку — кадр рисуется принудительно
  (`renderer.forceDraw()`): текстура могла остаться от другого размера или пропасть;
* авто-масштаб в статике не решает ничего и считает только по кадрам динамики —
  иначе по «быстрым» пустым интервалам уехал бы на 4×;* при выключенном авто-масштабе разрешение в простое не меняется: масштаб ручной —
  значит, его никто не трогает;
* счётчик «кадр» считает только нарисованные кадры, в отладке видно `up` и `idle`.

## Как данные идут на GPU

Два буфера, оба заполняются из `js/scene/pack.js → GE.writeFrame()` — это единственное
место, где задан порядок значений. Сцена приходит туда обычными числами.

**1. Uniform-буфер `Params` (48 float = 192 Б, `shaders/params.wgsl`):**

| float | поле | смысл |
|---|---|---|
| 0–1 | `resolution` | размер кадра в пикселях |
| 2 | `fov` | вертикальный угол обзора, радианы |
| 3 | `time` | игровое время сцены |
| 4–7 | `camPos` | позиция камеры |
| 8–11 | `camForward` | направление взгляда |
| 12–15 | `camRight` | вправо |
| 16–19 | `camUp` | вверх |
| 20–23 | `sunDir` | направление на солнце (единичное) |
| 24–27 | `sunColor` | цвет солнца + сила (0 — под горизонтом) |
| 28–31 | `skyAmbient` | цвет скайбокс-света (день/ночь считает CPU) |
| 32–35 | `counts` | сколько сфер, конусов, кубов (u32) |
| 36–39 | `extra` | яркость, тени (0/1), звёзды (0/1), разметка земли (0/1) |
| 40–43 | `frame` | `tan(fov/2)`, день 0…1, солнце над горизонтом 0…1, закат 0…1 |
| 44–47 | `frame2` | «день для поверхности» и цвет солнца, уже умноженный на силу |

Цвет и сила солнца, цвет неба — считаются на процессоре по углу солнца (`GE.sunFor`),
поэтому закат и ночь — это не ветки в шейдере, а числа. Последние две четвёрки — тоже
постоянные кадра: раньше `tan`, четыре `smoothstep` и умножение цвета солнца считались
в каждом пикселе, теперь — один раз в `pack.js`.

**2. Storage-буфер примитивов (`shaders/primitives.wgsl`):** один примитив = 3 × `vec4`
(48 Б), порядок в буфере — все сферы, затем конусы, затем кубы, смещения берутся из `counts`.

| примитив | `a` | `b` | `c` |
|---|---|---|---|
| сфера | центр + радиус | — | цвет |
| конус | точка A + радиус A | точка B + радиус B | цвет |
| куб | min (AABB) | max (AABB) | цвет |

Потолок буфера — 17576 примитивов (`MAX_PRIMS` в `js/gfx/renderer.js`), в сцене-стенде
занято 12, в бенчмарке — до 17576. Сцена упаковывается каждый кадр: 17576 примитивов — это
48 К float, загрузка буфера ≈192 КБ на кадр (около 0.6 мс процессора).

## Что внутри шейдера

Шейдер — перенос HLSL-версии (`raymarch.fx`) на WGSL. Осталось:

* хеши (`hash11`, `hash21`, `hash31`);
* звёздное небо: сетка ячеек по направлению луча, в каждой ячейке своя звезда;
* небо: градиент, закатная полоса у горизонта, диск солнца, ореол, рассеяние;
* земля: бесконечная плоскость `y = 0` с клетчатой сеткой, линии толще вдали;
* примитивы: сфера, усечённый конус (боковая поверхность + два торца), куб как готовый AABB;
* свет: скайбокс-свет + прямое солнце с жёсткой тенью + слабый блик и обводка;
* дымка к горизонту и дизеринг против полос на градиентах.

**Убрано насовсем** (по требованию к адаптации): все полупрозрачные объекты — призрачный
материал, аура из отрезков со слиянием стыков, поглощение `exp(-σ·d)`, цветные тени сквозь
оболочки, счётчики прозрачных слотов. Все тела непрозрачные, тени — жёсткие.

**Перенесено на CPU** (дороже на GPU, чем нужно): 4D-
срез, поворот куба (в буфер едет уже готовый осевой AABB), цвет и сила солнца, цвет неба,
матрица/базис камеры, а также все постоянные кадра из `frame`/`frame2`.

### Цена пикселя: что и почему сделано в шейдере

Кадр стоит «пиксели × (небо + земля + тела + лучи к солнцу)». На слабом GPU (телефон)
дорого именно то, что повторяется на каждом пикселе, поэтому:

* **постоянные кадра считает процессор** — `tan`, четыре `smoothstep`, умножение цвета
  солнца в пикселе больше не повторяются;
* **степени с целым показателем — умножениями** (`pow2`, `pow4`, `pow6`, `pow40`, `pow200`):
  на мобильных GPU `pow()` — одна из самых дорогих операций, а её было до семи на пиксель;
* **ветви, дающие ноль, не выполняются**: звёзды днём, у горизонта и рядом с солнцем; ореол —
  только вплотную к солнцу; блик — только там, где есть свет от солнца; разметка пола —
  только при включённой сетке; лучи к солнцу — только когда солнце над горизонтом и
  поверхность вообще может быть освещена;
* **для тени — отдельные проверки** `anySphere` / `anyCone` / `anyBox`: лучу к солнцу нужен
  только факт «тело на пути», а не точка попадания и не нормаль. Условия попадания те же
  самые, что у `hitSphere` / `hitCone` / `hitBox`, включая отсев граней, смотрящих от луча.

Сверка «до/после» на одних и тех же кадрах (день, ночь со звёздами, закат, сетка выключена,
17576 сфер): **расхождение по пикселям — ноль**, то есть картинка не поменялась вовсе.
Что это дало на nvidia pascal (сцена-стенд, 12 тел, кадр 4× = 2940×1652):

| случай | было | стало |
|---|---|---|
| тени включены | 18.2 мс | 9.7 мс |
| тени выключены | 11.1 мс | 10.0 мс |

## Что делать дальше (порядок предложен)

1. **Разные шейдеры на разные сцены**: сцена указывает свой `.wgsl`, рендерер пересобирает пайплайн.
2. **Постобработка отдельным проходом**: свечение, тонмаппинг.
3. **Буфер глубин и треугольники**: пройтись по сцене обычной растеризацией рядом с лучами
   и сравнить картинку — проверка «CPU ↔ GPU» на настоящих моделях.
4. **Текстуры с картинки**: `fetch` + `createImageBitmap` + `copyExternalImageToTexture`.
5. **Мягкие тени** вместо жёстких: несколько лучей на пиксель к диску солнца.
6. **Ускорение большого числа примитивов**: сетка/октодерево или экземпляры (instancing) —
   сейчас все тела перебираются на каждый луч, и это ровно то, что меряет бенчмарк.
   Зависимость там линейная (см. таблицу в разделе про бенчмарк), поэтому структура
   ускорения — следующий большой шаг, когда тел станет много.

## Рецепты правок

* **Новая сцена**: файл `js/scene/<id>.js` по образцу `demo.js` с `GE.Scenes.define({...})`,
  подключить его в конце `index.html` **после** `registry.js` и `pack.js`, добавить две
  надписи (`scene<Id>`, `scene<Id>Note`) в `strings.tsv`.
* **Свой набор ползунков**: собрать `params` и `toggles` в `define()` из `GE.SceneParts`
  или описать свои — `{key, label, fb, min, max, step, def, fmt}`; значения сцена получает
  в `update(dt, settings)`.
* **Кнопка сцены**: `actions: [{ key, label, fb, run: function (scene, settings) { … } }]`.
* **Новый объект в сцене**: дописать в `objects` — упаковка и счётчики подхватят его сами,
  пока не упрётесь в `MAX_PRIMS` (17576).
* **Другое положение камеры при открытии**: `camera: {target, yaw, pitch, distance, fov}`.
* **Новое значение с процессора**: поле в конец `Params` в `shaders/params.wgsl`, поднять
  `PARAMS_FLOATS` в `js/gfx/renderer.js`, записать значение в `pack.js → GE.writeFrame()`.
* **Новый переключатель нагрузки**: свободное поле в `extra` (`shaders/params.wgsl`) → ветка
  в `scene.wgsl` → значение в `writeParams` (в `pack.js`) → переключатель в `toggles` сцены
  или в `GFX_TOGGLES` (`js/ui/panels.js`), если он общий для всех сцен.
* **Новая строка статистики**: ячейка `<b>`/`<i>` в блоке `.perf-stats`, ссылка в `this.el`
  и заполнение в `HUD.setPerf()`.
* **Новая надпись**: ключ в разметку/код + строка в `strings.tsv`.
* **Новый цвет**: сначала пара переменных в `:root` и `html[data-theme="light"]` в `app.css`,
  в правилах — только `var(--…)`.

## Грабли

* `file://` не работает — только веб-адрес или локальный `http`.
* `timestamp-query` — фича необязательная. Если браузер не даёт поставить метки ни на
  кодировщике, ни внутри прохода, `gpu` показывает «—», а остальные цифры остаются верными.
* Время кадра — интервал между `requestAnimationFrame`, а не время работы GPU. Для fps
  берётся настоящий интервал (не ограниченный шагом сцены), поэтому на тяжёлых кадрах
  цифра честная; кадры после переключения вкладки (сотни миллисекунд) в статистику не берутся.
* Шаг сцены ограничен 50 мс: после паузы или подвисания сцена не прыгает вперёд.
* Номера строк в ошибках шейдера считаются по склеенному тексту (с вставленными
  `params.wgsl` и `primitives.wgsl`).
* Uniform-структура выравнивается по 16 байт: `vec2f` + два `f32` дают 16 Б, дальше только
  `vec4f`; `counts` — `vec4u` и пишется через `Uint32Array` поверх того же буфера.
* В WGSL нет тернарного `?:` (есть `select`), нет сложения вектора с числом
  (`vec3f * scalar` — да, `vec3f + scalar` — нет) и `smoothstep` с обратными краями
  даёт мусор — в шейдере все такие места переписаны через `1.0 - smoothstep`.
* Канвас создаётся только с `RENDER_ATTACHMENT`: чтение кадра обратно на CPU больше не нужно.
* Память настроек (`localStorage`, префикс `miniapps.game-engine.`): `gfx` — настройки
  рендера, `scene.<id>` — ползунки сцены, `activeScene` — какая сцена открыта. Старый общий
  ключ `settings` при первом запуске разбирается на эти три и удаляется.
* 17576 сфер на каждый луч — это честно дорого: по таблице в разделе про бенчмарк видно,
  что время кадра линейно по числу тел. Для игры столько объектов нужно ускорять
  структурой (сетка, октодерево, экземпляры).
* **Замер на невидимом канвасе врёт**: если рисовать в канвас, который браузер не показывает
  (сдвинут за экран), в замер влезает ожидание видимой поверхности — получается ровное
  «дно» ~140 мс независимо от размера кадра. Для честных замеров рисовать надо в свою
  текстуру (`RENDER_ATTACHMENT | COPY_SRC`) и ждать `queue.onSubmittedWorkDone()`; а на
  каждом кадре ждать нельзя — в ожидание влезает синхронизация (на этой машине ~2.5 мс),
  поэтому мерить пачкой кадров и делить на их число.
